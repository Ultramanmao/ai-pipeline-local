# v46.0: gpuq on 8 GB — Serializing Nine Workloads One Job at a Time, and the 53% Write-Loss Race That Broke Serialization

> Old Mao's Local AI Engineering Notes · 2026-10-24
>
> One-sentence hook: a 394-line stdlib task queue turned one shared 8 GB laptop GPU from a free-for-all into a strictly serial pipeline — and the bug that mattered wasn't in the GPU code at all, but in a file-replace race that silently lost 53% of the queue's file traffic, orphaned the running job, and let a second runner start.

---

## 1. The Goal / Problem

One laptop. One RTX 5060, 8 GB. Nine classes of workload that want it: ComfyUI image/video generation, FreeVideo FL2V burning, TTS voice synthesis, FunASR transcription, video super-resolution, a manual GUI app, model downloads, llama.cpp/ollama inference, and batch production kits.

On 2026-10-22 all of that collided the usual way. A six-segment video job (21 GB of weights) was burning the card while a TTS job was pushed into GPU mode alongside it. Both fell into VRAM swapping: a segment that normally takes ~10 minutes took **3.5 hours**. An entire morning, gone — not because anything crashed, but because two processes "weren't that big" and both ran anyway.

An audit of the nine entry classes found **zero** of them fully coordinated in any way (one was partially routed at best), and failure notification was almost universally missing (a background job could die and nobody would know). The fix had to be a queue that everyone goes through — plus one more thing: when something goes wrong at 3 a.m., the queue has to tell you, not wait to be asked.

The user's verdict became the spec: *from now on, everything runs serially. Build one middle platform that coordinates all GPU use. Never waste a morning like this again.*

So the design question is not "how do I schedule a GPU" in the abstract. It is narrower and meaner:

> How do you enforce strictly serial execution over a heterogeneous pile of shell commands and Python scripts, from an agent environment on Windows, with an unreliable network, and usually nobody watching?

## 2. The Design: Four Invariants

The whole tool is Python 3.14 standard library — no third-party deps, because a dependency that breaks on this MSYS/Windows mix is another failure mode. 394 lines at first delivery. What matters is not the size but the four concurrency invariants it had to hold, each learned from a specific way it can fail:

| # | Invariant | Why |
|---|---|---|
| 1 | Run lock is **atomically created** (`O_CREAT \| O_EXCL`) — never "read, then write" | Read-then-write locking has a window where two runners both think they hold the lock |
| 2 | Queue writes happen in a mutex region: temp file → `fsync` → `os.replace`; saves **merge** concurrent adds (append-only) | A whole-file rewrite silently drops tasks another process just registered |
| 3 | VRAM health check is **fail-closed**: if `nvidia-smi` can't be read or parsed, refuse to run | "Couldn't check" must not mean "assume it's fine" — checking before running is the whole point |
| 4 | Crash recovery marks leftover `running` records as explicit terminal state (`runner_interrupted`) — never auto-reruns | A task with side effects must not fire twice because the runner died |

Everything else — the watchdog, the diagnostics, the notifications, the bypass scanner — is built on top of those four.

| Component | What it is |
|---|---|
| Queue | `E:/workout/gpuq/queue.jsonl` — one JSON record per job (ts, name, est, cmd, log, status, attempts, rc, diagnostics paths…) |
| Lock | `gpuq.lock` holding PID + task name + heartbeat + random ownership token |
| Watchdog | Samples the task log every 30 s; zero growth for 180 s → kill process tree (`taskkill /F /T /PID`), snapshot, retry once |
| Hard timeout | est × 2 minutes (overridable), same handling as a stall |
| Diagnostics | Auto snapshot per attempt (`diag_<ts>_<name>_a1.txt`…): full `nvidia-smi`, `tasklist`, log tail, lock state |
| Notifications | Every event appends a self-contained line to `NOTIFY.txt`; a 5-minute cron watcher forwards new lines to chat channels |
| Sweep | `gpuq sweep` — reconciles `nvidia-smi` compute processes against queue records; reports bypassers, never kills |
| Wrappers | Thin `route_*.sh` shells around each entry class (original scripts untouched; rollback = delete the shell) |

## 3. The Box: What You Actually Type

```bash
python gpuq.py add <name> --est <min> [--vram-mb N] [--class cpu|gpu] [--timeout <min>] [--no-retry] [--priority] -- <command…>
python gpuq.py run            # drains the queue serially (one runner, lock-protected)
python gpuq.py wait <name>    # blocks until terminal state; exit code = task rc
python gpuq.py status         # lock + queue remainder + history counts
python gpuq.py release        # clears an orphan lock (only if the lock's PID is dead)
python gpuq.py sweep          # bypass reconciliation (report-only)
python gpuq.py selftest       # full self-check suite
```

Two semantics decisions did more for reliability than any amount of tuning:

**Class semantics.** `--class cpu` jobs skip the VRAM gate; `class=gpu` or undeclared jobs are fail-closed — if the card is occupied (used VRAM above the 2,000 MiB gate threshold), they *wait*, which is the entire point of serializing. The subtle case: resident services (ComfyUI server, the user's GUI app, ollama) sit on the card at idle with 0% utilization. Their memory holds the gate threshold open forever, so a client script that merely *submits* work would never pass a naive gate. The answer is not `--force`: submission scripts run as `class=cpu` (the GPU work happens inside the resident server, which is reconciled by sweep instead of queued), and `--force` stays an explicitly-flagged emergency bypass that skips even the 2,000 MiB threshold and must be mentioned in the notification line.

**Wrapper routing.** Each entry class gets a shell that does `add → run → wait` and propagates the task's exit code. The original scripts are never modified — the wrapper is a parallel file, so rollback is deleting a shell, not restoring an edit.

## 4. The Biggest Bug: 53% Write Loss Under a Concurrent Reader

This is the bug worth the whole article.

Symptom, from an independent audit's reproduction: hold a read handle open on `queue.jsonl`, then save five times in a row — **5/5 saves throw `PermissionError [WinError 5]`**. Extend it: a high-frequency reader against 2,000 saves produced **2,225 failed operations — 53% of the file traffic**.

Half the writes. Vanishing. On a queue whose only job is to not lose track of what is running.

Why it explodes: `os.replace` on Windows can fail with WinError 5/32 while a concurrent reader holds the file. Usually transient. But the exception path is what did the damage:

1. The write raises.
2. The exception escapes the task executor (`run_one → cmd_run`) and **crashes the runner**.
3. The `finally` block removes the run lock — while the task's child process is still alive.
4. Net result: an **orphan GPU task** holding the card, a **freed lock**, and a second runner free to start. Serialization — the one thing this tool exists to protect — is broken from the inside.

The fix is small and unglamorous (`gpuq_v2` fix batch R1):

- Treat replace/lock failures as **transient contention**: retry `PermissionError`/`WinError 5`/`WinError 32` ≥30 times with 0.05 s backoff before giving up; only throw after exhaustion. The outer save must not swallow the exception — an exhausted retry still has to be loud.
- Halve read pressure: `wait` polling goes from 0.5 s to 1.0 s.

Verification, because "the fix works" is not a claim, it's a test: race-test **case C** runs a child process hammering `load_queue` for 10 s while the parent saves ≥100 times, asserting zero exceptions, consistent line counts, and every line still valid JSON. Then the mutation knife: **remove the retry and case C must go red**. A green test that survives removal of the fix is decoration.

Windows-only addendum, same family of bugs: deleting the lock file can hit `WinError 32` when another process holds a read handle. Swallow that silently and you get orphan locks and failed concurrent registrations. Retry, like everywhere else in this tool.

## 5. The Watchdog: Log-Stall Protection, Not Health Detection

The watchdog samples the task's log size every 30 s and declares a stall after 180 s of zero growth, then kills the process tree, writes a diagnostic snapshot, and retries once by default.

This is not theoretical. The production queue carries a real kill-and-recover:

```
{"name": "dasiwa_fast4_demo2", …, "attempts": 2, "rc": 0, "elapsed_s": 200.7,
 "diags": ["E:/workout/gpuq/diag_20261023-071009_a1_dasiwa_fast4_demo2.txt"]}
```

Attempt 1 was killed by the watchdog mid-run (its diagnostic snapshot is the `_a1` file). Attempt 2 completed in 200.7 s. The queue moved on without anyone touching it.

But the honest description of this mechanism is: **it is stall protection, not health detection.** A quiet-but-healthy job (long video sampling writes nothing for minutes) can be killed. A dead loop that keeps printing can survive. The rules that follow from that:

- Big GPU jobs get an explicit `--timeout` — the hard timeout is the real backstop.
- Polling/waiting scripts must print a heartbeat line every cycle (`POLL <time> <status>`), even when nothing changed — a silent poller is indistinguishable from a hang.
- Never "fix" false kills by widening the threshold. A threshold wide enough to protect a quiet 60-minute render is wide enough to sleep through the VRAM-swap incident that started this project.

## 6. Beyond the Queue: Declare VRAM, Report Overuse, Reconcile Bypassers

Three additions from the v2 batch, each addressing a way "serial" can still leak:

**VRAM declaration.** Register with `--vram-mb N` and the runner pre-checks `memory.free` (3 samples × 2 s; any sample unreadable = fail-closed): free < N + 500 MiB refuses to start (rc=3, queue untouched). During the run, a 60 s sampler compares actual card usage to the declaration.

**OVERUSE is report-not-kill.** If actual usage exceeds N × 1.5, the queue emits an `OVERUSE` notification and keeps going. Real record from production:

```
{"name": "wst-fl2v-smoke", "vram_mb": 2500, "overuse": true, "overuse_mib": 5462, "overuse_count": 7, …}
```

A job that declared 2.5 GB was measured at 5,462 MiB on the card — seven notifications, zero kills. That is deliberate: killing a render 20 minutes in costs more than a few extra notify lines. The declaration is an admission ticket and a monitoring baseline, not a contract with a guillotine. (Same smoke suite later ran a clean 3,581.6 s — 59.7 min — job to rc=0 through the queue.)

**Sweep reconciliation.** `gpuq sweep` cross-checks `nvidia-smi --query-compute-apps` against queue `running` records — using recorded pid + child pid + a Toolhelp32 descendant walk, because jobs launch through `cmd`/`uv` wrappers and `nvidia-smi` only shows the leaf. Queue-external GPU processes get a `BYPASS` notification. Never a kill. Resident services (ComfyUI, the GUI app, ollama) go in a whitelist file so they don't flood the report; reports are deduplicated once per (pid, create-time). The acceptance bar for the routing work in progress: **three consecutive days of zero BYPASS**.

And one housekeeping rule that kept biting: the Ollama pre-clean (it eats ~25 GB of RAM and needs to die before big jobs) now only fires for `class=gpu` / declared / est ≥ 5 min jobs. Everything else gets an `OLLAMA_SKIP` note instead of a pointless restart.

## 7. Test Evidence

| Test | What it proves | Result |
|---|---|---|
| `selftest` 8/8 | add format, lock mutex, watchdog kill, status parse, orphan lock, NOTIFY write, taskkill format, path style | green |
| Race A1 | 12 rounds, two processes released at the same `perf_counter` instant, both calling `try_acquire_lock` | exactly one winner every round |
| Race A2 | 10 rounds, two end-to-end runners | one executes, one refused, task ran exactly once |
| Case M (mutation) | same A1 logic against a copy with `O_EXCL` stripped from the lock | must show ≥1 double-win round — i.e. the suite **must go red** when the primitive is removed |
| Case C (write contention) | 10 s of high-frequency reads against ≥100 saves | zero exceptions, line counts consistent, all JSON parseable |
| Case D (wait semantics) | two same-named jobs; `wait` returns on the *oldest* terminal one; ts_tag handle waits precisely | green; mutation back to `[-1]` goes red |
| 20 concurrent `add`s | merge semantics don't drop registrations | 20 rows, no loss |

The mutation cases deserve their own sentence. Before them, we shipped a lock test that passed **with `O_EXCL` deleted** — it only exercised the "existing lock with a live PID → refuse" path, which the missing primitive never touches. A second false-green taught the same lesson from the other side: a load probe reported "zero conflicts" while its own inline subprocess had failed to import — the load never ran, and the green number was measuring nothing. Rules now written into the tool's dev gate: **every concurrency primitive gets a mutation knife, and every probe verifies its own load is actually running before its numbers count.**

Rollout discipline (rollback-ready, per house rules): candidate file → `selftest` + sandbox tests → swap to production, old version kept as `gpuq.py.pre-hardening` / `gpuq.py.pre-v2b`, backups timestamped. v1 hardened went live 2026-10-22 23:15; the v2b fix batch went live 2026-10-23 09:33. Final production file: 1,592 lines, pure stdlib.

Before/after on the incident that started it: the colliding pair turned ~10-minute segments into **3.5-hour** ones. The queue doesn't make jobs faster — it makes them *alone*: every job above ran with nothing else touching the card, and that is the entire point.

## 9. What We Learned

1. **Mutation-test your locking primitives.** A concurrency test that stays green when the primitive is deleted is worse than no test — it manufactures confidence. We shipped exactly that once.
2. **On Windows, replace/lock errors are contention, not corruption.** Retry with backoff (≥30 × 0.05 s works); only treat exhaustion as failure. Silent swallowing leaves orphan locks; loud crashes leave orphan jobs — both are worse than a slow retry.
3. **An exception escaping the executor is worse than a failed task.** The runner died, the lock released, the child lived. Keep the failure inside the state machine where it becomes a record, not a crash.
4. **Fail-closed is the only safe default on a shared card.** Unreadable health data = refuse. The emergency bypass is explicit, flagged, and reported.
5. **Report-not-kill for overuse and bypass.** The queue's job is visibility and ordering. Execution policy for a 59-minute render belongs to the notification line, not the kill switch.
6. **The watchdog protects against stalls, not illness.** Timeout + heartbeats are the real health story.

## 10. What's Next

- **Entry routing (wrappers built, rollout in progress).** The audit found 9 entry classes and 0 fully routed. The wrapper shells all exist now — four low-difficulty routes (FreeVideo burn, super-res, TTS, batch kit) plus ComfyUI submitters (`class=cpu`) and ASR (`class=gpu`), originals untouched. What remains is rollout discipline and acceptance: sweep shows zero BYPASS for three straight days.
- **Notification chain is live.** Every queue event lands in `NOTIFY.txt`; a 5-minute cron watcher forwards new lines to chat channels, with its own crash alert so a dead watcher is itself a notification. Nobody should have to ask "did it finish?"
- **Better stall signals.** GPU utilization as an auxiliary input to the watchdog, so quiet-but-busy jobs stop being false-kill candidates.

## Summary

**A fail-closed, mutation-tested task queue turns a shared 8 GB GPU from a morning-destroying free-for-all into boring, predictable serial execution — and the bug that mattered was a 53% write-loss race that proved the tests, not the code, are where serialization is actually won.**
