**TL;DR** — A Chinese-only ASR model mis-transcribes any English word it hears. "DeepSeek" becomes 迪普搜索. "C U D A" becomes five characters with spaces. "Z-Image Turbo" becomes Z图像图博. In a pipeline that spends half its script talking about GPUs, CUDA, and LLM names, the subtitles were garbage. v18.0 adds a 17-line post-processor to `full_chain.py` that fixes them — before they burn into the video, not after.

---

## The symptom: subtitles that never ended

v17.0 shipped with a working split-compose-concat pipeline and a clean static background. The one remaining defect was subtler: the burned-in subtitles read fine when the script was purely Chinese, but the moment an English word appeared — "GPU", "DeepSeek", "CUDA" — the subtitle became nonsense.

This was not a FunASR bug. FunASR's `paraformer-zh` model was trained on Mandarin-only speech. When it hears an English token, it transliterates it phonetically the way a Chinese speaker would pronounce it. That is exactly what you want. The problem was that full_chain.py was burning that transliteration into the final video with zero post-processing.

A real transcript from a 35B benchmark script:

```
RTX五千零六十跑起三百五十亿参数的大模型显存只占三GB
不是硅速CPU推理而是每秒二十五token六万上下文
```

This one was actually clean — the model recognised RTX, GB, CPU, and token as-is. But try "DeepSeek" read aloud at the same speed and you get 迪普搜索. Try "ComfyUI API" and you get 康福UI接口. The mis-transcription rate depends on how unfamiliar the English word is to the Mandarin model.

## The fix: append-only post-processor

```python
def _fix_english_words(text):
    t = text
    for mangled, correct in _INTERLEAVED.items():
        t = t.replace(mangled, correct)
    for mangled, correct in sorted(_PHONETIC.items(), key=lambda x: -len(x[0])):
        t = t.replace(mangled, correct)
    t = re.sub(r'(?<=[\u4e00-\u9fff])\s+', '', t)
    t = re.sub(r'\s+(?=[\u4e00-\u9fff])', '', t)
    return " ".join(t.split())
```

Two lookup tables:

| Table | Purpose | Example |
|---|---|---|
| `_INTERLEAVED` | Letters spoken with inter-character spaces | `"C U D A"` → `"CUDA"` |
| `_PHONETIC` | Mandarin phonetic renderings of English words | `"迪普搜索"` → `"DeepSeek"` |

The `_PHONETIC` map starts with 10 curated entries, all of which are terms that actually appear in 8GB pipeline scripts:

```
迪普搜索       → DeepSeek
基米          → Kimi
康福UI        → ComfyUI
康福UI接口    → ComfyUI API
康福接口      → ComfyUI API
索引TTS       → IndexTTS2
索引TTS2      → IndexTTS2
Z图像         → Z-Image
Z图像图博     → Z-Image Turbo
Z图像图布     → Z-Image Turbo
```

The map is deliberately **append-only**. You only add a pair when you observe it in a real transcript. No guessing. No over-broad patterns. The code deliberately avoids mapping common Chinese characters to English equivalents — "米" (rice / Xiaomi) and "视频" (video) are left alone.

## What changed in full_chain.py

The hook is a single call inside `step2_stt()`, line 194:

```python
# --- post-process: fix English word mis-transcriptions ---
text = _fix_english_words(text)
```

The full `_fix_english_words()` function plus the two lookup tables are ~45 lines, all between `step2_stt` and `step3_compose`. Zero changes to `split_script`, `step1_tts`, `step3_compose`, or the concat logic.

## Pitfalls

- **Do not map common Chinese characters to English.** 米 (rice / Xiaomi), 视频 (video), 显卡 (graphics card) are real Chinese words that happen to have English equivalents — mapping them would corrupt legitimate Mandarin transcripts. Only map terms where the Mandarin rendering is itself a *transliteration*, not a translation.
- **Longest key first.** When "康福UI" and "康福UI接口" both appear, the 4-character form must match before the 2-character form. The code handles this via `sorted(..., key=lambda x: -len(x[0]))`.
- **The map is not auto-generated.** FunASR has no concept of "English word" — it outputs characters, period. Any future mis-transcription requires a manual addition to `_PHONETIC`. There is no ML-based auto-correction here; deliberate design choice.
