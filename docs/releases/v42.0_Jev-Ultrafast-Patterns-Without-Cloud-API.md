# v42.0: Jev Ultrafast's Speed Without Its Cloud API — What Transfers to Plain CDP and What Doesn't

> Old Mao's Local AI Engineering Notes · 2026-10-05
>
> A 3-week-old browser agent booked Google Flights in 7.07 s — but its brain is a paid closed model. We distilled its three loop patterns into plain CDP WebSocket code: decision probes on a real production SPA went from 5 round trips to 2, 73.2 ms to 3.6 ms median. Here is what transfers, what doesn't, and why the 20× number is the least interesting part.

---

## 1. The Goal / Problem

Browser automation burns time in the dumbest possible place: asking the page questions. The habit is serial and chatty — one `querySelector` probe per unknown, each its own protocol round trip, each reading a *different* page state. By the time you've confirmed the button, the list has re-rendered, your coordinates are stale, and the click lands on whatever moved into its place.

Jev Ultrafast (`browser-use/jev-ultrafast`, 22.1k stars three weeks in) attacks exactly this. Its loop reads the whole page as an indexed element table, makes the "which operation, which element" decision in **one** network round trip with a structured-decision model (TypeSafe Jev, 178 ms median), and only calls a text LLM when it must type. The headline demo: a real Google Flights search in 7.073 seconds.

The catch: the decision brain is a **closed, paid cloud API** (`TYPESAFE_API_KEY`), the DOM reader skips shadow roots, iframes, uploads and new tabs — and our production flows (multi-tab publishing on Chinese creator platforms) live in exactly those blind spots. So we didn't adopt it. We *mined* it: three loop patterns that fit in a plain CDP WebSocket session with zero new dependencies.

## 2. The Three Patterns

| Pattern | What it targets | Round trips per decision | GPU |
|---|---|---|---|
| 1. One-shot element table | Finding controls on an unknown page | 1 (was 3–6) | No |
| 2. Batch probe | Answering several unknowns consistently | 1 (was 1 per question) | No |
| 3. Click guards | Stale/mis-targeted clicks | 0 extra (folded into the probe) | No |

Everything below is copy-pasteable `Runtime.evaluate` JavaScript. No framework, no vendor.

## 3. Pattern 1: One-Shot Element Table

Stop interrogating elements one by one. One call returns the whole interactive surface as a numbered table; plan against the table instead of probing the DOM five times.

```javascript
(() => {
  const els = [...document.querySelectorAll(
    'button,input,textarea,select,a,[contenteditable="true"],[role="button"],[role="combobox"],[role="tab"]')];
  return JSON.stringify(els.slice(0, 60).map((e, i) => ({
    i, tag: e.tagName.toLowerCase(),
    role: e.getAttribute('role') || '',
    name: (e.getAttribute('aria-label') || e.innerText ||
           e.getAttribute('placeholder') || '').trim().slice(0, 40),
    value: (e.value || '').slice(0, 30),
    disabled: !!e.disabled,
    visible: !!(e.offsetWidth || e.offsetHeight),
  })));
})()
```

On a real production SPA (Xiaohongshu creator dashboard, note-manager view) this pulled the actual controls in 23 ms: a `button` named 打开创作助手 ("open creator assistant") and an `input` named 搜索已发布的笔记 ("search published notes"). The table is the planning surface — same trick jev uses, minus the proprietary model.

**Limits (same as jev's own):** common HTML/ARIA only. Shadow DOM and iframe contents do not appear in the table — for iframe file inputs we still use the objectId → `DOM.describeNode` → `DOM.setFileInputFiles` path.

## 4. Pattern 2: Batch Probe — One Snapshot, Many Questions

When a step depends on several unknowns — is the modal open? is the button there? how many cards loaded? — ask them all **in one evaluation**, so every answer comes from the same page state:

```javascript
JSON.stringify({
  url: location.href,
  modalOpen: !!document.querySelector('[role=dialog],.bcc-modal,.dialog-mask'),
  searchInput: !!document.querySelector('input[placeholder*="搜索"],.search-input,input[type=search]'),
  cards: document.querySelectorAll('.note-item,[class*="note-card"],.cover,.card').length,
  uploadBtn: !!document.querySelector('.upload-btn,[class*="upload"]'),
})
```

The consistency is worth more than the latency. Five serialized probes read five page states; on a live list view that means your "upload button exists" answer can be three renders out of date before you act on it. One batch probe gives one atomic snapshot.

## 5. Pattern 3: Click Guards

Before any critical click, one probe verifies the world is still as expected:

1. Target still exists, `visible`, not `disabled`
2. `scrollIntoView({block:'center'})`, then **re-read the rect** — animations and lazy loads invalidate old coordinates immediately
3. `location.href` is still the page you think (an agent sharing a window with a human will otherwise click into whatever tab the human switched to)
4. No overlay/dialog covering the target (Pattern 2's `modalOpen`)

After the click: read the **outcome** — toast, URL, counter, file count. "The click didn't error" is not success. jev states it bluntly: a `DONE` choice is never independent evidence of success. Our own production scars agree: double-clicked publish buttons create duplicate posts, and programmatic clicks on React action buttons can silently no-op.

## 6. The Honest Assessment

### What Actually Improved

- **Decision probes: 5 round trips → 2**, same information, on a real production SPA
- **Median probe latency: 73.2 ms → 3.6 ms** across 3 alternating pairs (20.3×), all three pairs won
- Every answer now comes from one consistent page snapshot — this is the real prize; stale-state mis-clicks are the failure mode we actually pay for

### What Didn't Improve

- Page loads, clicks, uploads, rendering: zero change. The 20× is probe-layer only
- Task-level speedups should be expected in the **~25% range**, not 20×: jev's own matched runs (6 alternating, one task) went 9.450 s → 7.092 s median — and that's with their 178 ms decision model in the loop
- Our test is n=3, one page, decision-probe workload. It is not an end-to-end agent benchmark, and jev's authors say the same about their own 3-pair comparison (p = 0.25)
- The element table doesn't reach shadow DOM, iframes, canvas, uploads, or new tabs — which is precisely why the full jev agent can't replace our multi-tab publishing flows

### Real Solutions

| Solution | Feasibility | Effectiveness |
|---|---|---|
| Adopt jev-ultrafast as-is | Low — closed paid decision API, blind in multi-tab/iframe flows | High where it works (single-tab form filling) |
| Keep deterministic CDP scripts + add the 3 patterns | High — zero dependencies, works today | High for reliability; ~25% for speed |
| Swap in a local structured-output model for Jev | Medium — the loop is MIT-licensed, the 178 ms latency is not | Unknown; untested |

## 7. Benchmarks

Our A/B (this machine, Windows, Edge 154 CDP on port 9222, same WebSocket session, read-only):

| Pair | Serial probes (5 calls) | Table + batch (2 calls) |
|---|---|---|
| 1 | 73.2 ms | 15.6 ms |
| 2 | 92.0 ms | 3.6 ms |
| 3 | 18.5 ms | 1.8 ms |
| **Median** | **73.2 ms** | **3.6 ms** |

Reference numbers, jev-ultrafast official (Google Flights task, their models):

| Metric | Original loop | Optimized loop |
|---|---|---|
| Median task time | 9.450 s | 7.092 s (−25%) |
| Browser protocol calls | 1,092 | 101 |
| Decision requests | 22 | 17 |
| Decision latency (median) | — | 178 ms |
| Text-generation cost per task | — | $0.00006 (OpenRouter) |

Different workloads: ours is decision-probe micro, theirs is end-to-end task. That's the point of putting them side by side — the probe-layer ratio (5–10×) is real, and it compresses to ~25% at task level.

## 8. What We Learned

1. **Round trips, not FLOPs, are the tax in browser automation.** jev cut protocol calls 1,092 → 101 and bought 25% task time; our probe cut 5 → 2 and bought 20× probe time. Same mechanism at both scales.
2. **Consistency beats latency.** An atomic snapshot matters more than the milliseconds saved — serialized probes on a live page answer questions about a page that no longer exists.
3. **A closed brain kills adoption even when the body is open.** MIT loop, paid decision model, `TYPESAFE_API_KEY` required — the patterns are free, the product is not. Read the architecture, keep the code.
4. **Click guards are the cheapest insurance in automation.** Four read-only checks before a click, one outcome read after, vs. re-uploading 20 images because a double-click posted twice.
5. **When a demo looks like sorcery, read `performance.md`.** jev's own doc carries the p = 0.25 caveat, the failure list, and the "DONE is not evidence" line. Honest repos hand you the boundaries — that's where the reusable ideas live.
