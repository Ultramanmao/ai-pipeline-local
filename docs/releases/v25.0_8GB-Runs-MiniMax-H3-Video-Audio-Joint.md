# v25.0: MiniMax H3 on 8 GB — Video + Audio Joint Generation, 33 GB of Models in 8 GB of VRAM

**TL;DR**: MiniMax H3 jointly generates video and synchronized stereo audio in one forward pass. The model stack totals 33 GB. On an 8 GB laptop, it runs in 14 minutes for a 5.9-second 1344×768 clip — using W4A8 quantization, NVFP4 32B encoder with CPU offloading, and a Turbo LoRA. The 4B encoder doesn't work (dimension mismatch). Block Cache doesn't help Turbo mode. But it produces real video with real audio, entirely local.

---

## 1. The Problem: H3 Is a Beast

MiniMax H3 is a video generation model that jointly produces video and audio in a single forward pass. No separate TTS, no audio post-processing — you type a prompt, it outputs an MP4 with synchronized voice, sound effects, and background music.

The catch: the model stack totals **~33 GB**.

| Component | Size |
|-----------|------|
| Diffusion model (W4A8 pruned) | 12 GB |
| Text encoder (32B NVFP4 AWQ) | 15.7 GB |
| Video VAE (fp16) | 4.9 GB |
| Audio VAE (fp32) | 578 MB |
| Turbo LoRA (lightx2v) | 301 MB |
| ClipProj | 291 MB |
| **Total** | **~33.7 GB** |

A laptop RTX 5060 has 8 GB VRAM. That's a 4:1 mismatch.

## 3. The Node Chain

H3 runs inside ComfyUI as a chain of custom nodes. Two modes:

### T2V (Text-to-Video)

```
UNETLoader(W4A8) → MiniMaxH3TurboLoRA(lightx2v, low_vram=true)
    → BasicGuider + BasicScheduler(steps=6) + RandomNoise
    → SamplerCustomAdvanced
CLIPLoader(32B NVFP4, type=minimax)
    → MiniMaxH3ImageToVideo(prompt, 1344×768, 125帧)
SamplerCustomAdvanced
    → VAEDecode(video VAE) + VAEDecodeAudio(audio VAE)
    → CreateVideo(fps=24) → SaveVideo(format="auto")
```

### I2V (Image-to-Video) — Recommended

Same as T2V, plus a first frame input:

```
LoadImage(first_frame.png) → MiniMaxH3ImageToVideo(first_frame=[LoadImage, 0])
```

Skip Klein entirely if you have an existing photo. Load any image directly into the `first_frame` input — no preprocessing needed.

I2V output is **3.3× larger** than T2V (3.9 MB vs 1.2 MB) — significantly more detail because the first frame anchors the diffusion.

## 4. The Biggest Bug: 4B Encoder Is a Dimension Trap

This one killed an entire afternoon.

**Symptom**: `mat1 and mat2 shapes cannot be multiplied (32x2560 and 5120x5376)`

**What happened**: The h3lite repo's Set A suggests using the 4B INT4 encoder (`qwen3vl_4b_int4_convrot.safetensors`, 2.6 GB). It's small, it fits in VRAM, it should work.

It doesn't.

H3's `condition_proj` layer expects **5120-dim** input (32B encoder output). The 4B encoder outputs **2560-dim**. This is a hard architectural constraint — no adapter, no projection trick, no workaround.

| Encoder | Output Dim | Fits H3? | Size |
|---------|-----------|----------|------|
| 4B INT4 ConvRot | 2560 | ❌ Dimension mismatch | 2.6 GB |
| 32B BF16 | 5120 | ✅ But 51.5 GB | 51.5 GB |
| 32B INT8 ConvRot | 5120 | ✅ But 27.1 GB | 27.1 GB |
| **32B NVFP4 AWQ** | **5120** | **✅ Fits with CPU offload** | **15.7 GB** |

**Fix**: Use the 32B NVFP4 encoder. It's 15.7 GB — won't fit in 8 GB VRAM, but ComfyUI's automatic CPU offloading handles it. Every step, the encoder weights shuttle between RAM and VRAM. Slow, but it works.

**Download gotcha**: NVFP4 uses HuggingFace xet storage. hf-mirror.com stalls at 0% for xet files. Use modelscope.cn instead:

```bash
curl -4 -L -C - -o "qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors" \
  "https://modelscope.cn/models/Comfy-Org/MiniMax-H3/resolve/main/text_encoders/qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors"
```

~4 MB/s, 15.7 GB in ~50 minutes. 2× faster than hf-mirror.

## 5. Pitfalls We Hit

### Block Cache: Useless for Turbo Mode

Installed `comfyui-minimax-h3-blockcache-T8` hoping to skip stable blocks and save time.

Result: **every step refreshed the cache**. Residual diffs (0.25–0.73) far exceeded the 0.12 threshold. Zero cache hits. Zero speedup.

**Why**: Turbo LoRA makes large per-step changes (few steps, high denoise per step). Block Cache is designed for 20-step normal sampling where consecutive steps are similar. They're fundamentally incompatible.

### 4 Steps Lose Detail

The LoRA is called "lightx2v_turbo_**4step**", so 4 steps should be optimal, right?

No. 4 steps produce noticeably less detail than 6 steps. The ~33% time cost increase (from ~512s to ~785s) is worth the quality.

| Steps | Time (T2V) | Quality |
|-------|-----------|---------|
| 4 | 512s | Soft, lost细节 |
| **6** | **785s** | **Sharp, recommended** |
| 8 | ~1050s | Marginal improvement |

### low_vram Doubles the Time

Without `low_vram=true`, the LoRA merge uses extra VRAM → OOM on 8 GB. With it, LoRA merges into base weights each run → extra compute.

| Config | Time |
|--------|------|
| Without low_vram | ~14 min (but OOM on 8 GB) |
| **With low_vram** | **~24 min** |

8 GB cards have no choice. Accept the ~55% slowdown.

### SaveVideo Format Must Be "auto"

ComfyUI v0.34.1's SaveVideo node: `format` must be `"auto"`, not `"video/h264-mp4"`. Otherwise: `TypeError: missing 1 required positional argument: 'format'`.

### stderr Must Redirect to File

ComfyUI's tqdm progress bar calls `flush()` on stderr. Windows pipes trigger `OSError: [Errno 22] Invalid argument`. Fix:

```bash
python main.py --listen 2> comfyui.log
```

### First Frame ≠ Lip Sync

H3 jointly generates video + audio, but the audio is **ambient sound, music, SFX** — not speech lip-sync. The mouth doesn't move with the audio.

For talking-head videos: H3 video → IndexTTS2 voiceover → SadTalker lip-sync. H3 replaces the "background video + ambient audio" part, not the speech pipeline.

## 6. Benchmarks

All tests on **RTX 5060 Laptop, 8 GB VRAM, 32 GB RAM, ComfyUI v0.34.1**.

| Config | Resolution | Duration | Steps | Time | Output Size |
|--------|-----------|----------|-------|------|-------------|
| T2V (preview) | 864×480 | 0.9 s | 6 | 62 s | 68 KB |
| **T2V** | **1344×768** | **5.9 s** | **6** | **785 s (13 min)** | **1.2 MB** |
| T2V + BlockCache | 1344×768 | 5.9 s | 4 | 512 s | 1.0 MB (less detail) |
| I2V (Klein首帧) | 1344×768 | 5.9 s | 6 | 834 s | 3.9 MB |
| **I2V (已有图片)** | **768×1344** | **5.9 s** | **6** | **917 s** | **2.0 MB** |
| **I2V (low_vram)** | **768×1344** | **5.9 s** | **6** | **1422 s (24 min)** | **1.4 MB** |

**Sweet spot for 8 GB**: 125 frames (5.9 s @ 24 fps). Going to 192 frames (8 s) makes each step 5.4× slower — not worth it.

### Why It's Slow

The 15.7 GB encoder + 12 GB diffusion model can't coexist in 8 GB VRAM. ComfyUI offloads the encoder to CPU, and every sampling step shuttles weights across the PCIe bus. That's 106 s/step at 1344×768 — but it works.

## 7. What We Learned

1. **W4A8 + NVFP4 + Turbo LoRA is the only viable combo for 8 GB.** The 4B encoder doesn't fit the architecture. INT8/BF16 encoders don't fit in VRAM. NVFP4 with CPU offloading is the narrow path.

2. **ModelScope > HuggingFace Mirror for xet files.** hf-mirror.com stalls on xet storage. modelscope.cn gives 4 MB/s steady. 2× faster, reliable resume.

3. **I2V beats T2V by 3.3× in output size.** The first frame anchors the diffusion — more detail, more coherence. Always use I2V if you have a frame.

4. **125 frames is the 8 GB sweet spot.** Doubling to 192 frames makes each step 5.4× slower due to memory pressure. 5.9 seconds is enough for a short clip.

5. **H3 does ambient audio, not speech.** The joint video+audio generation produces background music and SFX. For talking heads, you still need TTS + SadTalker.

6. **Block Cache and Turbo don't mix.** Turbo LoRA makes large per-step changes. Block Cache expects small residual diffs. Fundamentally incompatible.
