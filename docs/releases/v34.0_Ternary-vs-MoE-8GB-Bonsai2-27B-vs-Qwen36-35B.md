# v34.0: Ternary vs MoE on 8 GB: Bonsai 2 27B vs Qwen3.6-35B — Same Score, 3.6× Smaller

> Old Mao's Local AI Engineering Notes · 2026-09-23
>
> Two roads to a big LLM on an 8 GB laptop GPU — ternary quantization vs MoE sparse activation. 30 benchmark questions later: identical scores, identical failures, near-identical speed. One model is 3.6× smaller and the only one that fully fits in VRAM.

> Date: 2026-09-23 · GPU: RTX 5060 Laptop 8 GB · CUDA: 13.3 · Runtime: PrismML llama.cpp fork + llama.cpp · OS: Windows 11 native
> Release: https://github.com/Ultramanmao/ai-pipeline-local/releases/tag/v34.0

**TL;DR:** Bonsai 2 27B Ternary (5.6 GB, all weights compressed to {-1, 0, +1}) and Qwen3.6-35B-A3B Q4_K_M (20 GB, 3B of 35B active per token) scored exactly the same on 30 benchmark questions — 27/30 each, down to failing the same three GSM8K items with the same wrong numbers. Speed is a wash (32.15 vs ~30 tok/s). Footprint is not: 5.6 GB vs 20 GB on disk, ~6 GB vs ~20 GB in memory. On an 8 GB GPU, dense ternary beats MoE — and the only question left is where quantization cracks first.

---

## 1. The Question

There are two competing philosophies for running a big LLM on small hardware:

- **Quantize everything harder.** Keep the dense architecture, squeeze each weight below 2 bits. Bonsai 2 27B packs every weight as a trit {-1, 0, +1} at 1.72 bits per weight — 27B dense parameters in a 5.6 GB file.
- **Activate less.** Keep more bits per weight but only run a fraction of the network per token. Qwen3.6-35B-A3B is a 35B-parameter MoE that activates only 3B per token — at Q4_K_M that's a 20 GB file that has to straddle GPU and CPU on an 8 GB machine.

Both claim "big-model quality, small-hardware cost". [v15.0](https://github.com/Ultramanmao/ai-pipeline-local/releases/tag/v15.0) showed Bonsai 27B can live on 8 GB; [v21.0](https://github.com/Ultramanmao/ai-pipeline-local/releases/tag/v21.0) crowned the Qwen3.6-35B MoE the 8 GB sweet spot. This release puts the two winners in the same room: 30 questions, same harness, same conditions.

## 2. The Two Approaches

| | Bonsai 2 27B Ternary | Qwen3.6-35B-A3B MoE |
|---|---|---|
| **Base model** | Qwen3.8-27B (PrismML ternary compression) | Qwen3.6-35B |
| **Architecture** | 27B dense, all active | 35B total, **3B active/token** |
| **Quantization** | PTQ1_0 ternary {-1, 0, +1}, **1.72 bpw** | Q4_K_M, 4-bit |
| **File size** | **5.6 GB** | 20 GB |
| **Memory placement** | **~6 GB — pure GPU** | ~20 GB — GPU + CPU hybrid |
| **Engine** | PrismML llama.cpp fork | llama.cpp |
| **Measured speed** | **32.15 tok/s** | ~30 tok/s |

The paradox is right there in the table: the dense 27B model runs **faster** than the MoE that activates 3B per token. Weights-not-compute is the binding constraint at this tier — Bonsai is fully resident on the GPU, while Qwen3.6-35B spends its cycles on CPU offload.

## 4. Round 1: Basics — Both Score 15/15

| Model | GPQA | MMLU | GSM8K | Total | Wall time | Per question |
|---|---|---|---|---|---|---|
| Bonsai 2 27B Ternary | 5/5 | 5/5 | 5/5 | **15/15** | 207 s | 13.8 s |
| Qwen3.6-35B MoE | 5/5 | 5/5 | 5/5 | **15/15** | 214 s | 14.3 s |

No separation. Not on accuracy, not on speed. The hard band is where quantization is supposed to show damage — so let's go there.

## 5. Round 2: Hards — Both 12/15, and They Fail *Identically*

| Model | GPQA (Hard) | MMLU (Hard) | GSM8K (Hard) | Total | Wall time | Per question |
|---|---|---|---|---|---|---|
| Bonsai 2 27B Ternary | 5/5 | 5/5 | 2/5 | **12/15** | 323 s | 21.5 s |
| Qwen3.6-35B MoE | 5/5 | 5/5 | 2/5 | **12/15** | 330 s | 22.0 s |

Both models nailed the brutal stuff — QED Landau poles, Claisen six-membered rings, tRNA suppressors, the no-BEC-in-2D proof, r_s ∝ M scaling, P=NP framing, O(n^2.37) matrix multiplication. Both died on multi-step arithmetic:

| GSM8K (Hard) item | Bonsai answer | Qwen answer | Correct |
|---|---|---|---|
| Inventory problem | 115 | 115 | **120** |
| Compound interest | 1157.63 | 1157.63 | **1157.625** |
| Work-rate problem | 5 | 5 | **5.5** |

Same three failures. Same wrong numbers. This is the single most useful data point in the whole test: **the failure fingerprint is identical**, which means the errors come from the shared Qwen-family base models' weakness in chained arithmetic precision — not from quantization. If the ternary conversion had damaged reasoning, Bonsai would fail where Qwen succeeds. It doesn't fail anywhere Qwen doesn't.

## 6. The Honest Assessment

### What Actually Improved

Nothing needed to improve — the test was a head-to-head. What it **proved**:

- **Ternary 1.72 bpw costs zero measurable quality** vs 4-bit MoE on knowledge + reasoning MCQs (27/30 = 90% for both).
- **Dense ternary beats MoE on an 8 GB budget**: 3.6× smaller on disk (5.6 vs 20 GB), 3.3× smaller in memory (~6 vs ~20 GB), fully GPU-resident vs CPU-hybrid, and still slightly faster (32.15 vs ~30 tok/s).

### What Didn't Improve

- **GSM8K multi-step arithmetic is broken in both.** Compression didn't cause it and compression can't fix it. Rounding-sensitive chains (1157.625 → 1157.63) die in both models' reasoning traces.
- **Speed parity is not a ternary win.** 32.15 vs ~30 tok/s is within noise of different engines and different placement strategies. The honest claim is "no speed penalty", not "faster".

### Real Solutions

| Goal | Solution | Feasibility | Effectiveness |
|---|---|---|---|
| Best LLM on 8 GB GPU | Bonsai 2 27B PTQ1_0 (5.6 GB) | ✅ pure GPU | 27/30 quality, 32 tok/s |
| Best LLM on 24 GB+ | Either — pick by license/features | ✅ | quality tie |
| Uncensored + GPU-accelerated | Need a PTQ1_0 uncensored build (CRACK only ships PQ2_0 — see §7) | ⚠️ not found yet | — |
| Fix arithmetic failures | Tool use / calculator augmentation, not better quantization | ✅ | targets the actual weakness |

## 7. The Pitfall: A 6.8 GB File That Won't Fit in 8 GB

While chasing an uncensored build I downloaded `dealignai/Bonsai-2-27B-Ternary-CRACK-GGUF` — the abliterated variant in PQ2_0 format, 6.8 GB. "6.8 GB fits in 8 GB", right?

```
failed to fit params to free device memory
```

GPU load: **failed**. The 6.8 GB of weights plus runtime overhead (KV cache, CUDA context, compute buffers) overflowed the 8 GB VRAM budget. Fallback to CPU gave **2.2 tok/s** generation (7.3 tok/s prompt processing) — unusable.

The difference is the trit packing format:

| | PTQ1_0 (standard) | PQ2_0 (CRACK) |
|---|---|---|
| Packing | dense trits, **1.72 bpw** | one trit per 2-bit slot, **2.13 bpw** |
| File size | **5.6 GB** | 6.8 GB |
| GPU fit on 8 GB | ✅ 32 tok/s | ❌ OOM → CPU 2.2 tok/s |
| CPU fallback speed | 7.6 tok/s | 2.2 tok/s |
| Uncensored | no | **yes (abliterated)** |

A 21% size difference from packing format alone decides GPU vs CPU — a 14× speed difference. PTQ1_0's dense packing needs the PrismML fork's custom kernels; PQ2_0 trades size for engine compatibility. On this hardware, that trade is the whole ballgame.

The PTQ1_0 setup that works:

```bash
cd E:/WSL/bonsai/runtime/prism-cuda133
./llama-server.exe -m "E:/WSL/bonsai/models/Bonsai-2-27B-PTQ1_0.gguf" \
  -ngl 99 -c 8192 --jinja --reasoning on \
  --temp 1.0 --top-p 0.95 --top-k 20 --host 127.0.0.1 --port 8080
```

**Lesson: "fits in 8 GB on paper" ≠ "fits at runtime".** Budget ~1.5–2 GB over the weights for KV cache and compute, and check the packing format before you pick a download.

## 9. Limitations

1. **30 questions is a smoke test, not a leaderboard.** It separates models that differ meaningfully; it cannot rank models that are close.
2. **Multiple-choice favors both models.** Open-ended generation and long-form writing could separate them — quantization damage tends to show up in fluency before it shows up in recognition.
3. **Chinese is untested.** How 1.72-bpw ternary compression treats CJK tokens is an open question.
4. **Long context and agent workloads untested** (tool loops, structured output over long prompts).

## 10. What We Learned

1. **Ternary 1.72 bpw is free at this tier.** 27/30 vs 27/30 — three quantization levels down (fp16 → 4-bit → ternary), zero measured quality loss on knowledge/reasoning MCQs.
2. **Identical failure fingerprints isolate the real weakness.** When two differently-compressed models fail the same items with the same wrong answers, look at the base model, not the quantizer.
3. **Multi-step arithmetic is the shared crack** in the Qwen family at these sizes — chained rounding (…1157.625) collapses in both.
4. **On 8 GB, dense ternary beats MoE.** The MoE's 3B-active advantage is eaten by CPU offload; the dense ternary model is smaller in memory than the MoE's on-disk file.
5. **Packing format is a hardware decision.** PTQ1_0 (1.72 bpw, custom kernels) vs PQ2_0 (2.13 bpw, compatible) is 5.6 vs 6.8 GB — GPU-resident 32 tok/s vs CPU 2.2 tok/s on an 8 GB card.

## What's Next

- **Open-ended + Chinese comparison** — long-form generation is where ternary compression should crack first if it's hiding damage.
- **Hunt for a PTQ1_0 uncensored build**, or test partial offload (`-ngl 40`) on the PQ2_0 CRACK as a middle ground.
- **MTP speculative decoding on Bonsai's fork** — [v23.0](https://github.com/Ultramanmao/ai-pipeline-local/releases/tag/v23.0) got +92% from one flag on Qwen3.8; the PrismML fork is a different codebase and worth probing.

## Summary

**On 8 GB, 1.72-bit ternary density matches 4-bit MoE quality exactly while using 3.6× less disk and fitting fully in VRAM — the compression-vs-sparsity race is over at this tier.**
