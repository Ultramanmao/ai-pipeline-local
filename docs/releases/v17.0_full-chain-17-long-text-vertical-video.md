**TL;DR** — A single Python file that turns 300 characters of script into a 40-second, 1080×1920 vertical video with voiceover, auto-transcribed subtitles, and zero manual editing. v17.0 splits long scripts into segments automatically, runs the v16.0 one-command pipeline per segment, then stitches them with FFmpeg concat. The fix that got this past the finish line: swapping the blurry 768×512 LTX-2B video background for a native 1088×1600 Z-Image Turbo still frame. The pipeline is the real story; the background swap was the one-line fix hiding in a 300-character search.

---

## v16.0's ceiling: 60 characters

v16.0 shipped last week as "one command, one clip." Text in, MP4 out. 30 seconds. Beautiful.

It also had a hard ceiling: the FFmpeg drawtext filter and the audio duration both assumed a single continuous clip. Anything past ~60 characters of script (≈ 60 seconds of speech) would force a single SRT block spanning the whole video, with one giant subtitle box at the bottom. Readable, yes. Polished, no.

The question wasn't *can it do long scripts* — it obviously could. The question was *does the code actually split them*.

---

## The pipeline: split → compose × N → concat

```
script ("300 chars...")
    |
    |-- split_script() -- 8 segments @ 45 chars each
    |
    |-- seg_01.wav (IndexTTS2)
    |-- seg_01.srt  (FunASR paraformer-zh)
    |-- seg_01_clip.mp4  (FFmpeg: bg + audio + drawtext)
    |
    |-- repeat × 7 ...
    |
    |-- concat (FFmpeg demuxer) --> final.mp4 (1080×1920)
```

The split logic lives in `split_script()`: sentence-boundary cuts (。！？；), then a merge pass that tacks fragments shorter than 4 characters onto the previous chunk, then a hard max-45-character cap with a fallback to the last comma. Three passes, no dependencies.

Per segment is identical to v16.0. The only new code is the loop and the concat step.

## The background: a 768×512 mistake

v16.0 used a 768×512 LTX-2B video as the background. FFmpeg's `force_original_aspect_ratio=decrease` fit it into 1080×1920 by scaling *down*: 768 wide × 512 tall → shrunk to fill the width, then padded with 600 pixels of black above and below. The video occupied roughly **40% of the frame**. Not blurry — just invisible behind the black bars.

The original fix attempted `increase` (scale up and crop), but 768→2880 interpolation introduced upscaling blur on the anime character, and the background was animating — unnecessary for a voiceover clip where the speaker is the only thing that matters.

The real fix was a one-liner: **swap the video for a 1088×1600 Z-Image Turbo still**. 1088 × 1600 is close to 1080 × 1920, so `decrease` scales it *down* only a few pixels — zero upscaling, sub-5px black bars, and the background is static so it can't fight with the speaker. The Z-Image workflow (seed 42, 4 steps, 41 seconds on 8 GB, lowvram):

| Field | Value |
|---|---|
| ckpt | zImageFp8_turboRev11.safetensors |
| sampler | ZSamplerTurbo2Simple //ZImagePowerNodes |
| steps | 4 |
| seed | 42 |
| latent ratio | 3:2 (photo) |
| output size | 1088 × 1600 |
| VAE | ae.safetensors |
| wall time | 41s (lowvram) |

The background reads "professional financial dashboard at midnight" — navy blue fading to crimson, a faint bokeh light spot on the right edge, nothing else. No text, no clutter, no competing shapes.

## What actually shipped

v17.0 is backward compatible. Short text (under 60 chars) runs the original single-segment v16.0 path untouched. Long text auto-splits. `--no-split` forces v16.0 behavior. `--video` now accepts either a video file or an image — the code inspects the extension and switches the FFmpeg filter chain:

| Input | Filter |
|---|---|
| Image | `scale=1080:1920:force_original_aspect_ratio=decrease,pad=1080:1920:…` |
| Video | `scale=-2:1920,crop=1080:1920:…` |

Both output 1080×1920 with burned drawtext subtitles and AAC audio.

## Pitfalls

- **FFmpeg `force_original_aspect_ratio` only accepts `decrease`, `increase`, `ignore`.** `width` is not a valid value. Attempting it produces "Undefined constant" — no output, no warning to a human.
- **`-loop 1` must come *before* `-i`** for static images. `ffmpeg -loop 1 image.png` silently drops the input stream.
- **FFmpeg filter_complex `:` parsing eats Windows paths.** Every path into a filter chain must go through `_rp()` (relative to FFMPEG_CWD). Absolute paths like `E:/workout/…` are parsed as filter parameters.
- **ComfyUI Z-Image latent must use `medium (recommended)` and `3:2  (photo)`** — the literal strings, not the shortened forms. Wrong values silently fail with an unhelpful node error.
