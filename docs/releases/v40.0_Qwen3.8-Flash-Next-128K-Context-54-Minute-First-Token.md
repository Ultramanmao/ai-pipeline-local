# v40.0: Qwen3.8-Flash-Next 177B on 8 GB: 128K Context Holds, a 35K-Token Document Answers 3/3, and the 54-Minute First Token

> Date: 2026-10-04 · GPU: RTX 5060 Laptop 8GB · CUDA: cu132 · Framework: llama.cpp build 10793 (d230ddd76) · OS: Windows 11 native
> Release: https://github.com/Ultramanmao/ai-pipeline-local/releases/tag/v40.0

**TL;DR:** In v37.0 we got a 72.5 GB / 177B model running on an 8 GB laptop. This release asks the next question: **how much context does that actually buy?** Three tiers measured (8K / 32K / 128K): cold prefill degrades only **−25.9%** from 8K to 128K (5.98 → 4.43 t/s) against a pre-registered <50% line — the hybrid linear-attention architecture is doing exactly what it promises. A real 34.8K-token document + three questions with answers **locked in writing before the test**: **3/3 correct, zero hallucination.** But two operational traps dominate the experience: (1) sending a long document through bare `/completion` makes the model **instantly emit EOS** (empty answer after a 50-minute prefill) — long-doc QA must go through the chat template; (2) the first question's first token lands after **54 minutes** (3237 s TTFT at 10.7 t/s prefill on this GPU). The fix for the second is the prefix cache: **Q2/Q3 hit cache_n=32705 and answer in ~3 minutes** instead of 54. Decode speed at 35K context is honestly slower (1.6–2.6 t/s). Full pre-registered scorecard included — one prediction (KV vs dense at same context) is explicitly marked *unverified*.

## 1. The Question

v37.0 (2026-09-29) established that a 72.5 GB UD-IQ1_S MoE runs on 32 GB RAM + 8 GB VRAM: 6.11 t/s, 56/60 on an ability suite, no 1-bit collapse. Every reader's next question is the same one we had: *"okay, but can it actually use its 256K context window, or is that a spec-sheet number?"*

Context is where 8 GB setups usually die — KV cache grows with sequence length, and dense models get expensive fast. But this architecture is not dense: **48 layers = 12×(3×(Gated DeltaNet→MoE) + 1×(QSA sparse attention→MoE))** — 36 of 48 layers are linear-attention layers with constant state. The prediction this suggests is testable, so we tested it with predictions pinned first.

## 3. B1 — Context Tier Curve (8K / 32K / 128K)

Same model, same prompt shape (519-token probe, `n_predict 64`, temp 0, 2 reps), only `-c` changes. Cold rep = full prefill on a fresh slot.

| Tier | pp t/s (cold) | tg t/s (cold) | pp t/s (cached) | tg t/s (cached) | Peak working set | Peak private bytes |
|---|---|---|---|---|---|---|
| `-c 8192` | 5.98 | 6.38 | 14.60 | 8.14 | 25.69 GiB | 10.10 GiB |
| `-c 32768` | 4.85 | 5.72 | 13.92 | 8.01 | 25.71 GiB | 10.96 GiB |
| `-c 131072` | 4.43 | 5.68 | 13.09 | 7.90 | 25.49 GiB | 14.77 GiB |

**Prefill degradation 8K → 128K: 5.98 → 4.43 t/s = −25.9%** — comfortably inside the pre-registered <50% line (✅). Generation speed drops only −11% (6.38 → 5.68). For comparison, on dense models of this size class, prefill typically degrades much more steeply with context.

**Memory:** going 8K → 128K costs **+4.67 GiB private bytes** (10.10 → 14.77 GiB) — that is the KV expansion plus buffers. Working-set peak stays ~25.5 GiB across all tiers (dominated by weight page cache, insensitive to KV). Configuration: `n_slots=4`, `kv_unified=true`, `n_ctx_slot` = tier value.

**Prediction B2 verdict: NOT VERIFIED.** We claimed "3–4× less KV than dense" but never ran a dense model at the same context as a control. We report the absolute numbers and mark the comparative claim unverified — a prediction without a baseline is a hypothesis, not a result.

## 5. Trap #1 — Bare `/completion` Eats Long Documents

The first attempt sent the concatenated document straight to `/completion`. Prefill ran for **3023.7 s** (34,741 tokens @ 11.5 t/s)... and then the model **immediately emitted EOS**: empty text, `predicted_n=1`, TTFT null. Fifty minutes of prefill, zero answer.

Cause: the raw completion endpoint does not apply the chat template, so the model reads the document's ending as a natural end-of-sequence. It is not a context failure — it is an interface failure.

**Fix:** run long-doc QA through `/v1/chat/completions` with `--jinja` (chat template). Same model, same document, immediately works. If you script long-document pipelines against llama.cpp servers, this one will burn an hour of your life if you don't know it.

## 6. Trap #2 — The 54-Minute First Token (and the Cache That Saves It)

Final run configuration: stock build, `-ngl 8 -c 65536 -ub 2048 --jinja --reasoning off`, `/v1/chat/completions` streaming, `max_tokens 512`, temp 0.

| Q | cache_n | prompt_n | pp t/s | TTFT | gen t/s | wall |
|---|---|---|---|---|---|---|
| Q1 | 0 | **34,753** | 10.74 | **3236.9 s ≈ 54 min** | 1.58 | 3242 s |
| Q2 | **32,705** | 2,047 | 10.62 | 193.1 s ≈ 3.2 min | 2.22 | 199 s |
| Q3 | **32,705** | 2,047 | 10.87 | 188.5 s ≈ 3.1 min | 2.57 | 194 s |

Q1's prefill walks 34.7K tokens at ~10.7–11.25 t/s (server progress lines, one per 2048-token batch, ~180 s per batch — slow decay from 11.25 to 10.76 t/s). On an 8 GB card, **a 35K-token document's first answer is an hour-scale event.** Plan for it.

Then the prefix cache does the heavy lifting: Q2 and Q3 hit **cache_n=32,705** — the document prefix is reused wholesale, only the question + template tail (2,047 tokens) recomputes. **54 minutes → 3 minutes** for every follow-up question on the same document. The practical shape of long-doc work on this hardware is therefore: **one slow cold question, then a fast interactive session.** Batch your questions; don't restart the server between them.

Honest note on decode: at 35K context, generation runs **1.6–2.6 t/s**, clearly below the 5.7–8.1 t/s of the short-prompt tiers. Decode degrades with sequence length on this stack — reported as measured, no smoothing.

## 9. What We Learned

1. **The architecture's promise checks out at the tier that matters.** −25.9% prefill degradation at 128K is the linear-attention layers doing their job. This is the first "spec sheet claim survives contact with an 8 GB laptop" in our 177B series.
2. **Interface choice can cost an hour.** The bare `/completion` EOS trap is silent — no error, just an empty answer after a 50-minute prefill. Chat template for anything document-shaped.
3. **Prefix cache is the difference between usable and unusable** for long-doc work here: 54 min → 3 min per follow-up. Keep the server alive and the document prefix stable.
4. **TTFT is the real context-limit UX metric, not max context.** 128K *fits*; whether you can *wait* for it is a separate question. Budget hours for cold prefill on GPU-poor hardware.
5. **A prediction without a baseline is not a result.** The KV-vs-dense claim looked reasonable, but with no dense control we mark it unverified rather than "confirmed by vibes."

## 10. Honest Limits

- **One model, one quantization (UD-IQ1_S), one machine.** Tier curve and TTFT numbers are this stack's, not universal constants.
- **The QA corpus is our own notes** (34.8 KB). Great for verifiable ground truth; not a benchmark of general long-doc reasoning. 3/3 on three lookups ≠ solved retrieval.
- **Only lookup-type questions tested.** Synthesis across a 35K-token corpus (e.g. "summarize the four notes' conflicting conclusions") is untested and likely slower.
- **B2 remains unverified** (§3) — the dense-KV comparison needs its own run.
- **No 256K-tier test.** 131072 was our ceiling this round; 256K native would need a bigger `-c` and more patience than a 54-minute TTFT already demands.

## 11. What's Next

- Dense control run at matched context to close B2 (KV comparison)
- Synthesis-type questions on the same corpus (beyond lookup)
- 256K tier on the roadmap when there is a real use case worth the prefill
- The series' remaining side story: vision tests (OCR 12/12 zero-hallucination, but fine spatial comparison is the real weak spot) — coming separately
